# Testing

## Unit tests (any host, Python 3.11+)

From a git checkout; release archives do not include the tests. To run them on a server with Debian's real SPF/DKIM/DNS libraries, copy `src`, `tests`, `etc` and `scripts` from the checkout (`tar -czf pw-src.tgz src tests etc scripts`), unpack them in a scratch directory and run the command below there as an unprivileged user.

```sh
PYTHONPATH=src python3 -m unittest discover -s tests/unit -t tests/unit
```

Covers address parsing and normalization, configuration validation, reply validation, reading `mynetworks`/`recipient_delimiter` from Postfix, the policy matrix (protected addresses, protected groups and transport, self-sender, visible From, SPF/DKIM combinations, null-sender rule, deadlines), the callback layer against a PyMilter stub (observe/enforce, RCPT vs end-of-message replies, local pickup accumulation, transaction isolation, size, header, recipient and open-message limits) the installer (Postfix rendering against the local `postconf`, concurrent-edit and symlink refusal, rollback including a first install, activation records and their predecessors, the detached state before attachment, Postfix-only repair, switch order and recovery from a failed restart or reload), per-section modes and their composition (an observed refusal never skipping an enforced check, forced limit deferrals), sending limits (limit keys and multipliers, reservations under concurrency, rolling windows, the key store at a small capacity, the local cap, the state file's strict load and atomic save, observe/enforce/off), `lookup` and `stats` sources and counts from lines the daemon itself formats (including the DKIM rate and coverage), DKIM diagnostics (verdicts identical with diagnostics on and off over the SPF/DKIM cross-product, verifier call counts, result words, the cut `dkim=` list and `dkim_summary`), and `simulate` against the callback layer. SPF/DKIM tests use the installed `spf`, `dkim` and `dns` modules when present and stand-ins otherwise; on a host without them they do not exercise real verification. These prove policy logic only; they are not evidence about Postfix, DNS, libmilter or delivery.

## Load and capacity

`tests/load/milter_load.py` (checkout only, standard library) talks to a postwarden socket with the milter protocol, as Postfix does, and presents every message as untrusted port-25 mail from `192.0.2.0/24` with a `gmail.com` sender, so SPF fails (softfail). Nothing is queued or delivered. Run it against a second daemon on a test socket, so live mail and the mail log are untouched:

```sh
install -d -o postwarden -g postwarden -m 0750 /tmp/pwload
runuser -u postwarden -- /usr/local/sbin/postwarden run --stderr --socket unix:/tmp/pwload/policy.sock 2>/tmp/pwload/daemon.log &
python3 tests/load/milter_load.py --socket unix:/tmp/pwload/policy.sock --messages 200 --concurrency 20
python3 tests/load/milter_load.py --socket unix:/tmp/pwload/policy.sock --messages 20 --concurrency 10 --signatures 10 --body-kib 40000
python3 tests/load/milter_load.py --socket unix:/tmp/pwload/policy.sock --hold 105
kill %1
```

`--peer` sets the client addresses presented (a network, cycled), so SPF can pass for a domain whose record lists them; nothing is sent, so the load host's own address does not matter. `--sign-key` signs every message for `--dkim-domain`/`--selector` with a real key instead of random signatures (needs `python3-dkim`; an RSA key in the traditional form, `openssl genrsa -traditional`). `--sign-pattern` sets the signatures top to bottom: `pass`, `fail` (changed `b=`), `missing` (unpublished selector) or `broken` (the selector `broken`, published with a malformed key):

```sh
python3 tests/load/milter_load.py --socket unix:/tmp/pwload/policy.sock --messages 200 --concurrency 20 \
  --peer 198.51.100.16/29 --sender load@example.org --dkim-domain example.org --selector load \
  --sign-key /root/load.private --sign-pattern fail,fail,pass    # example.org: your test domain, its SPF listing the --peer network
```

The tool reports throughput, latency percentiles and the replies by stage, and exits non-zero if any message took longer than `--slow-after` (default 60 s, Postfix's `content_timeout`) or failed. Messages carry syntactically valid but unverifiable `DKIM-Signature` headers for a real selector (default `gmail.com`/`20230601`; its key is now revoked, so they log `permerror`, and a published key gives `fail`).

Which path a run measures depends on the daemon's configuration; check the `reason=` and `dkim=` fields in its log:

| Daemon setting                                                                                      | Path measured                                                | Expected log                                                                                              |
| --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| default `require = "both"`                                                                          | SPF only: the SPF failure decides and DKIM is skipped        | `reason=spf_softfail dkim=skipped`                                                                        |
| `require = "either"` (a copy of the configuration passed with `postwarden --config <copy> run ...`) | SPF, then a DKIM key lookup and full body hash per signature | `reason=no_aligned_pass dkim=gmail.com:permerror,...`, or `evaluation_incomplete` when the deadline is reached |

Keep the body plus headers below `limits.message_bytes` (40960 KiB by default): `--body-kib 40960` alone exceeds it and every message is deferred as `message_bytes` before any SPF/DKIM work. The signatures are negative fixtures (random `b=`/`bh=`); they measure lookup and hashing cost, not verification of a valid signature. `--hold N` opens N transactions at `MAIL FROM` and keeps them open: with the default `max_open_messages = 100`, 100 get `continue` and the rest `451 4.7.1`; a new transaction succeeds after they are released.

## Rollback and reinstall

```sh
python3 scripts/install.py rollback --deployment-id <active-deployment> --dry-run
python3 scripts/install.py rollback --deployment-id <active-deployment> --apply
# verify delivery/signing, then
python3 scripts/install.py configure-postfix --apply
```
