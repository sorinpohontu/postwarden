# ADR-0033: A Date beyond a tolerance is rejected by its own section

- Status: Accepted (design); implementation pending
- Date: 2026-10-09

## Context

Spam is often sent with a `Date` field in the future, so that it stays on top of
inboxes sorted by date. Nothing in Postwarden looks at `Date`. Postfix
`header_checks` cannot compare against the current time: a year pattern needs
editing every year, misses days or months ahead, cannot apply a timezone-aware
tolerance and covers every cleanup pass alike. The reference estate's
`header_checks` file is also regenerated by its infrastructure project.

## Decision

- New section `[message_date]` with its own `mode = "observe" | "enforce" | "off"`,
  default `observe` (ADR-0022), and `max_future`, default 24 hours. Log rule
  `rule=future_date`. It joins the sections that decide `failure_action`
  (ADR-0023).
- Checked on every ingress path (25, 587, 465, mynetworks, local pickup),
  with `allow_local = true` and `allow_mynetworks = true` exemptions like
  `[sender_authentication]`. Authenticated submission has no exemption.
- Evaluated at end of message against the server clock. Every `Date` field is
  parsed; if any parses to more than `max_future` ahead, the message violates the
  rule. A missing or unparseable `Date` passes and is logged with a reason. A
  `-0000` or zoneless date is read as UTC. Past dates are never refused.
- Enforce rejects with a configurable 5xx reply, default
  `550 5.7.1 Message date is in the future`; observe logs `would_reject`.
- The log carries `date_skew=<seconds>` and the parsed time as normalized UTC
  ISO 8601, never the raw header value.
- Ships in 1.3 as item E, independent of B–C. The same pure check runs in
  `simulate`; `stats` counts the rule.

## Consequences

- A client with a fast clock beyond 24 hours gets an immediate 5xx on
  submission; cron or appliance hosts are covered by the exemptions.
- A local pickup refusal follows Postfix's non-SMTP end-of-message behavior.
- Not taken: `header_checks` (no clock); untrusted port 25 only (forged future
  dates via submission go unchecked); a key in `[sender_authentication]` (not
  an authentication result, and it would share that mode); first `Date` only
  (evadable with a second field); refusing missing, malformed or old dates
  (separate decision; queued, resent and list mail is legitimately old);
  defer instead of reject (a retry does not change the header).
